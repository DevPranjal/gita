# gita v0.3

*— the long-running agent's debugger.*

v0.2 finished the read companion: `get`, `diff --symbol`, `prove`,
`last-proven`, three-state glyphs. The agent can now ask *"what does this
symbol look like?"* and *"what's the last known-good state?"* without
re-reading source.

v0.3 closes the loop. When something is broken between *known-good* and
*HEAD*, the agent should be able to ask gita **which structural change
broke it** — and get back an op, not a sha.

---

## customer

Same one customer as v0.2. Nothing branches yet.

> A single autonomous coding agent in hour 3 of a session. It just ran its
> own test suite and one check is now red that was green an hour ago.
> Today, it bisects by re-reading commits. Tomorrow, it asks gita.

Not the customer for v0.3 (still parked):

- Agent swarms / multi-agent merge — that's the v0.4 conversation.
- Maintainer / review agents — they want intent metadata; revisit when
  `prove` and `bisect-proven` have real users.
- Inline / one-shot edit agents — still hold the file, still marginal.

---

## what v0.2 already does

| verb              | does                                                              |
| ----------------- | ----------------------------------------------------------------- |
| `diff`            | structural diff, `--symbol` filter, `parseable: false` on non-py. |
| `get`             | symbol shape at any rev, walks one rename hop backward.           |
| `explain`         | manifest for a commit, with proof glyphs.                         |
| `symbol-log`      | per-symbol history with proof glyphs.                             |
| `callers`         | reverse-call lookup over the manifest index.                      |
| `prove`           | record `<name> -> {ok, exit, stdout-head/tail}` against HEAD.     |
| `last-proven`     | last commit where all (or one named) recorded checks were ok.     |
| `mcp`             | stdio JSON-RPC for all of the above. 8 tools.                     |

v0.3 keeps every one of these and adds one new pillar, sharpens one
existing pillar, and ships three small wins.

## 01 · `bisect-proven` — net-new pillar

The reason this exists: when `pytest` is green on commit `A` and red on
HEAD, the agent today either re-runs `git bisect` (slow, no insight) or
reads every commit between (slow, blows the context window). Both treat
the substrate as opaque.

gita already has both ends of the answer: `prove` says which commits were
ok, and the manifest says which ops happened between them. Composing them
is a new verb, not a new system.

```sh
gita bisect-proven pytest
gita bisect-proven pytest -- python -m pytest tests/auth
gita bisect-proven pytest --symbol fetch_user
gita bisect-proven pytest --json
```

### behaviour

1. Resolve the *suspect range*: `from = last-proven pytest`, `to = HEAD`.
   If `last-proven` is empty → exit with a hint to run `gita prove` first.
   If `from == HEAD` → exit 0, "nothing to bisect, HEAD is the last
   proven commit."
2. If a `-- <cmd>` is supplied, run it on `HEAD` first. If it passes,
   refresh the proof and exit 0 ("HEAD passes — recording proof, no
   bisect needed."). This makes the verb safe to call speculatively.
3. Walk the suspect range, newest first. For each commit, *if a proof
   exists*, use it. Otherwise (and only if `-- <cmd>` was supplied)
   check the commit out, run the command, record the proof, restore.
4. Narrow to the **first failing commit** — the one whose parent is the
   last green commit in the range.
5. Read that commit's manifest and pick the **smallest set of ops** that
   could plausibly explain a regression. Report symbol-level, not
   line-level.

### output

```text
$ gita bisect-proven pytest
range:   3b22ff (✓) → a91f2c (✗ HEAD), 6 commits
suspect: 88e1d0  "wip: faster lookup"
  body      fetch_user      -1/+0  removed `if not authorize(req): return 403`
  callers   fetch_user      2 (handle_get, handle_post) — both still call it
hint:    `gita get fetch_user@88e1d0~1` for the prior shape
```

```json
{
  "from": "3b22ff…",
  "to":   "a91f2c…",
  "suspect": {
    "commit": "88e1d0…",
    "message": "wip: faster lookup",
    "ops": [
      {"kind": "body", "symbol": "fetch_user", "path": "src/users.py",
       "added": 0, "removed": 1}
    ],
    "callers_of_changed_symbols": {
      "fetch_user": ["handle_get", "handle_post"]
    }
  },
  "checks_used": {"3b22ff…": "cached", "88e1d0…": "ran", "a91f2c…": "cached"}
}
```

### scope rules — what `bisect-proven` is *not*

- Not a replacement for `git bisect`. It only narrows over commits that
  already have proofs *or* over a single named check when invoked with
  `-- <cmd>`. It will never try arbitrary heuristics.
- Not a fixer. It reports the suspect op; it does not propose a patch.
- Not interactive. There is no `gita bisect-proven good` / `bad`. The
  whole point is that `prove` made bisection non-interactive.
- Not for unproven baselines. If `last-proven <name>` is empty, the
  verb refuses and tells the agent to prove first. Cheaper to fix the
  missing input than to invent one.
- Not symbol-causal. `--symbol fetch_user` filters reported ops to ones
  touching that symbol; it does not claim those ops caused the failure.
  That's the agent's call, not gita's.

## 02 · `diff` — composite read for one MCP round-trip

`get`, `symbol-log`, `callers`, and `last-proven` already exist as
separate verbs. An agent debugging one symbol today makes four MCP
calls and burns four turns. v0.3 adds one verb that composes them.

```sh
gita context fetch_user
gita context fetch_user --budget 2000   # max tokens (rough)
gita context fetch_user --json
```

Output (text mode):

```text
fetch_user  function  src/users.py:14-22
  def fetch_user(uid: str) -> User | None:
      ...

callers (2):
  handle_get   src/api.py:31
  handle_post  src/api.py:48

recent commits (3):
  a91f2c  ✗ pytest  body -1/+0
  88e1d0  ✗ pytest  body -1/+0     ← first failing
  3b22ff  ✓ pytest  add caching

last proven (pytest): 3b22ff
```

This is the verb the long-running agent actually wants. `--budget` is a
soft token cap: oldest commits and lowest-priority sections drop out
first; the result always fits.

### scope rules

- Composition only. No new data is computed that the four underlying
  verbs don't already produce.
- `--budget` is best-effort. The verb never returns a partial body or a
  half-truncated line; sections are atomic.
- One symbol per call. Multi-symbol "give me everything about these five
  things" is a v0.4 conversation — solving it well needs ranking.

## 03 · the small wins shipping in v0.3

These are not separate pillars. They're each a few hours of work that the
agent has been visibly bumping into.

### `gita who [<rev>]`

Show git author + (optional) agent identity from env vars:

```text
$ gita who HEAD
author:  Pranjal Gulati <pg@example.com>  2026-05-26 13:08
agent:   claude-3.7-sonnet  session=a8c1  prompt-hash=4f2e…
```

Reads `GITA_AGENT_MODEL`, `GITA_AGENT_SESSION`, `GITA_AGENT_PROMPT_HASH`
out of the commit's notes (set by `gita commit-note` or by the agent
runtime). No crypto, no enforcement — a label, not a signature. The
crypto pillar from inspiration.md is still parked.

### `gita explain --json` and `gita bisect-proven --json`

Both already half-exist (`explain` has a text mode; `bisect-proven` is
new). `--json` is mandatory from day one for any agent-facing verb. v0.3
audits the surface and adds `--json` everywhere it's missing.

### post-commit auto-prove (opt-in)

A tiny `gita install-hooks` writes a `post-commit` hook that re-runs the
checks last recorded on HEAD's parent, against the new HEAD. So after
the agent commits, gita silently updates proofs without the agent
remembering. Opt-in, removable, never installed without `install-hooks`.

### manifest cache for `callers`

Today `gita callers` re-reads every per-tree caller manifest. On this
repo it's instant; on a 5k-file repo it's not. Add a tiny in-process LRU
keyed by `(tree_sha, symbol)`. Pure perf, no API change.

## storage

No new top-level directories. v0.3 adds two things under `.git/gita/`:

```
.git/gita/
  manifests/<commit_sha>.json     # unchanged
  callers/<tree_sha>.json         # unchanged
  proofs/<commit_sha>.json        # unchanged
  notes/<commit_sha>.json         # new — optional agent identity
  hooks-installed                 # new — sentinel, set by install-hooks
```

Notes are optional. Their absence is silent. They never affect any other
verb's behaviour.

## mcp surface

Three new tools, one extension:

| tool                 | maps to                                                  |
| -------------------- | -------------------------------------------------------- |
| `gita_bisect_proven` | `gita bisect-proven <name> [-- cmd] [--symbol s]`        |
| `gita_context`       | `gita context <symbol> [--budget N]`                     |
| `gita_who`           | `gita who [<rev>]`                                       |

Existing `gita_explain` gains a no-op compat field for `--json`-only
clients (it already returns JSON; this is a doc fix). Nothing removed.

## what's coming after v0.3 (not in scope, but on the record)

v0.4 is shaping up around two things: **structural merge** (op
composition for multi-agent work) and **`gita tui`** (a Textual-based
interactive view over the same library functions that today's CLI and
MCP server already use). The TUI is a view layer, not new substrate;
it's parked until v0.3 ships `context` + `bisect-proven`, because those
are what populate it. Sketch + scope lives in `specs/v0.4.md`.

## non-goals for v0.3

Spelled out so they stop coming up:

- **Structural merge / op composition algebra.** This is v0.4's headline.
  Designing it without `bisect-proven` in users' hands is premature.
- **`gita tui`.** Also v0.4. See preview above.
- **Multi-language parsing past Python.** Still tier-2 textual fallback.
  Adding TS/JS is a v0.3.1 or v0.4 conversation; v0.3 is about depth on
  the existing surface, not breadth.
- **Multiverse / speculative branches.** Still wrong customer.
- **Cryptographic agent identity / signed proofs.** `gita who` deliberately
  ships only the label form. Promote to signatures when a customer asks.
- **`gita gc` for proof retention.** Still tiny, still unbounded, still
  fine. Add only when someone complains.
- **Bisecting trees, not commits.** Proofs are commit-keyed and stay so.

## open questions

Flagging for review, not blocking:

1. **`bisect-proven` and merge commits.** A merge commit's manifest
   combines two parents' ops. Reporting "the merge broke it" is true
   but useless. Proposal: when the suspect is a merge, recurse into the
   merged-in side first and report the suspect commit on *that* side.
   Cap recursion at 1 hop.
2. **`gita context` ranking.** With `--budget` cramped, which sections
   go first? Proposal: signature → body → first failing commit → last
   proven sha → callers → older commits. Drop from the tail.
3. **Auto-prove hook performance.** Re-running pytest on every commit
   is fine for some agents and obnoxious for others. Proposal: the hook
   only re-runs checks marked `auto: true` in a new
   `.git/gita/proofs.config.json`. Default = none auto. Opt-in twice.

---

## done means

v0.3 is shippable when:

- `gita bisect-proven <name>` narrows to the first failing commit *over
  cached proofs alone* and reports the suspect ops.
- `gita bisect-proven <name> -- <cmd>` fills gaps by running the command
  on intermediate commits and recording proofs as it goes.
- `gita context <symbol>` returns symbol shape + callers + recent
  symbol-log + last-proven in one call; `--budget N` always returns
  something that fits.
- `gita who` reads commit notes for agent identity; absent notes render
  silently (no garbage rows).
- Every agent-facing verb has `--json`.
- `gita install-hooks` installs an opt-in post-commit auto-prove that
  only runs checks marked auto.
- `callers` is fast on a 5k-file synthetic repo (cached lookup).
- Tests cover: bisect over cached proofs only; bisect with `-- cmd`
  filling gaps; bisect refusal on no baseline; bisect on a merge
  commit; context output ordering under `--budget`; `who` with and
  without notes; auto-prove hook running only opted-in checks; cache
  hit on `callers`.
