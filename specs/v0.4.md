# gita v0.4 — preview

*Not a commitment. A holding pen so the v0.3 non-goals list has a place
to point.*

v0.3 finishes the read+debug loop for one agent. v0.4 is where gita
starts being interesting for **more than one** agent and for **humans
watching the agent work**.

Two pillars. Independent. Either could ship first.

---

## pillar A · structural merge

When two branches edit the same file, git diffs lines and surfaces
conflicts at line ranges. gita already knows the *operations* each
branch performed on the manifest — most of those ops compose without
human help.

```
$ gita merge feat-A
auto-merged 7 ops, 1 conflict:
  body of fetch_user: both branches modified.
    show with: gita merge --show fetch_user
```

| branch A op            | branch B op            | gita verdict        |
| ---------------------- | ---------------------- | ------------------- |
| add `foo`              | add `bar`              | auto-merge          |
| rename `foo`→`fooX`    | edit body of `foo`     | auto-rewrite the edit onto `fooX` |
| body of `foo`: +1/-0   | body of `foo`: +2/-0   | symbol-level conflict |
| import + `lru_cache`   | import + `partial`     | auto-merge          |
| signature `foo`        | body `foo`             | auto-merge          |
| delete `foo`           | edit body of `foo`     | conflict, surfaces both |

### why this isn't v0.3

- Needs op-composition tables that should be derived from real
  customer collisions, not guessed in advance.
- Needs writeback (re-emitting source from a merged op set), which is
  a different substrate from anything v0.1–v0.3 ships.
- Solving this without anyone running `bisect-proven` is premature —
  the same agent debugging itself is a smaller, sharper problem.

### scope guess (not a commitment)

- Tier 1: same-file, disjoint symbols → trivial auto-merge.
- Tier 2: rename + edit on the same symbol → auto-rewrite.
- Tier 3: same-symbol body conflicts → symbol-level conflict markers,
  not line markers. (Better than git, not magic.)

## pillar B · `gita tui` (interactive view)

Textual TUI. Same library functions the CLI and MCP already call. No
new substrate.

```
┌─ gita ────────────────────────────────────────────────────────────────┐
│ symbols     │  fetch_user           function  src/users.py:14-22     │
│ ──────────  │  ──────────────────────────────────────────────────    │
│ ▸ User      │    def fetch_user(uid: str) -> User | None:           │
│ ▾ users.py  │        row = db.lookup('users', uid)                  │
│   fetch_user│        if row is None:                                │
│   delete_…  │            return None                                │
│ ▸ handlers  │        return User.from_row(row)                      │
│             │                                                        │
│ commits     │  callers                                               │
│ ────────    │  ─ handle_get   src/api.py:31                         │
│ ✗ a91f2c    │  ─ handle_post  src/api.py:48                         │
│ ✗ 88e1d0  ◀ │                                                        │
│ ✓ 3b22ff    │  recent                                                │
│ · d04a81    │  ✗ a91f2c body -1/+0                                  │
│             │  ✗ 88e1d0 body -1/+0   ← first failing (bisect)       │
│             │  ✓ 3b22ff add caching                                  │
│             │                                                        │
│ [/] search  [b]isect  [g]et @rev  [d]iff  [p]rove  [q]uit            │
└───────────────────────────────────────────────────────────────────────┘
```

### panels (sketch)

- **left top — symbol tree**: file → symbol, expandable. Selecting a
  symbol drives every other panel.
- **right top — symbol body**: live shape of the selected symbol at
  the selected rev. Same data as `gita get`.
- **left bottom — commits**: filtered to commits touching the selected
  symbol; proof glyphs on the left. Same data as `gita symbol-log`.
- **right middle — callers**: same data as `gita callers`.
- **right bottom — recent ops**: per-commit op summary lines, marked
  with `← first failing` when `bisect-proven` has a suspect.

### keybindings (sketch)

| key | action                                     |
| --- | ------------------------------------------ |
| `/` | fuzzy-find symbol                          |
| `b` | run `bisect-proven` against current check  |
| `g` | open `gita get` at arbitrary `@rev`        |
| `d` | open `gita diff` for the selected range    |
| `p` | run `gita prove` for the configured check  |
| `q` | quit                                       |

### why this isn't v0.3

- TUI is a view; views need verbs to view. `bisect-proven` and
  `context` (v0.3) are the verbs that make this layout worth drawing.
- Textual is fine but pulls a dependency tree gita has so far avoided.
  Worth it once, not as a side-effect of an unrelated phase.
- Painting screens before the underlying data is stable invites two
  rewrites instead of one.

### scope guess (not a commitment)

- One screen, five panels, the keys above.
- No mouse mode in v0.4. Keyboard-only.
- Reads only. The TUI never writes — writes still go through the CLI
  so the audit trail (and the agent's own use of gita) stays uniform.

## non-pillars

These are still parked, even in v0.4:

- Multiverse / speculative branches.
- Cryptographic agent identity / signed proofs.
- Multi-language parsing past Python (still tier-2 textual fallback;
  TS/JS lives in its own minor release whenever someone needs it).
- `gita gc` for proof retention.

---

## what would make this real

A real customer running `bisect-proven` and complaining about exactly
one of:

1. *"merging my agent's branches by hand is killing me"* → ship A first.
2. *"I can't watch what my agent is doing"* → ship B first.

Both are plausible. Neither is urgent until v0.3 is in hands.
