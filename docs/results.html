Does it actually work?

Eighteen tasks across Flask, Express, Gin, ripgrep and got. Two arms: a coding agent with plain git, and the same agent with gita also on PATH. gita is never mentioned in the prompt — it has to be discovered and chosen, or it does not count.

108 runs — three repetitions of every task in both arms. The cost figure carries a 95% interval of −6% to −39%, bootstrapped over tasks. Dropping the 16 runs that lost the prompt cache — noise priced at 12.5×, unrelated to either tool — gives −16.7% on a tighter interval of −6% to −27%. Treat −16.7% as the number.

two claims that did not survive more data

This page previously reported tool output −92%, from ten tasks. On eighteen it is +0.4% — no difference at all. That figure had been carried by a single lockfile task and it collapsed once the corpus was large enough to dilute it. gita's own output is small; the agent then spends the saving falling back to raw git, which is the real problem and is being worked on.

It also reported −15.4% as the headline. That point estimate compared arm totals while the interval printed beside it paired by task. On a balanced sweep the two agree exactly, which is how the discrepancy survived fourteen sweeps. Paired, those same runs read −17.9%.

Both corrections are recorded rather than quietly dropped, because a benchmark that only ever revises upward is not a benchmark.

how it is measured

The agent is not told

gita is put on PATH and described in the repository's AGENTS.md exactly as any other repo tool would be. The task prompt never names it. If the agent does not find it useful, it does not use it, and that counts against gita.

Cost is real, not a proxy

Priced in credits from the model's own logs, across four token classes that differ in price by 50x. Token totals mislead in both directions: fresh output is billed at up to 12.5x the rate of cached context.

Quality is scored as entity recall — whether the agent's final answer names the things the change actually touched. A cheaper answer that misses the point is not a win, so cost is only ever read next to recall.

how to read these numbers

Turn count is the steady signal; the cost figure is the imprecise one. Cost carries a 95% interval of −6% to −27% after cache-noise is removed — real, but eighteen tasks differ from each other far more than repetitions of one task do, so the aggregate can only be resolved so far. Turns matter most anyway, because a turn re-sends the entire context.

Tool output is no longer a signal at all. It was, on ten tasks; on eighteen the two arms are level. Reporting it as a win would mean keeping a number that stopped being true when the sample grew.

Recall is 96% for git and 97% for gita. Both are held down by one task whose answer key demands the name of a test the commit deletes; both arms answer it the same way, so the comparison is unaffected and the key is being corrected.
