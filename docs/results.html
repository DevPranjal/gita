Does it actually work?

Ten tasks across Flask, Express, Gin, ripgrep and got. Two arms: a coding agent with plain git, and the same agent with gita also on PATH. gita is never mentioned in the prompt — it has to be discovered and chosen, or it does not count.

how it is measured

The agent is not told

gita is put on PATH and described in the repository's AGENTS.md exactly as any other repo tool would be. The task prompt never names it. If the agent does not find it useful, it does not use it, and that counts against gita.

Cost is real, not a proxy

Priced in credits from the model's own logs, across four token classes that differ in price by 50x. Token totals mislead in both directions: fresh output is billed at up to 12.5x the rate of cached context.

Quality is scored as entity recall — whether the agent's final answer names the things the change actually touched. A cheaper answer that misses the point is not a win, so cost is only ever read next to recall.

what the numbers cannot support

A control sweep moved ten points on its own

One sweep was repeated with byte-identical behaviour — the only change was in the scoring code. The headline moved ten points, and one individual task moved 82.

So at three repetitions, per-task cost numbers are noise, and any story told from them is a story about noise. Published figures pool six repetitions per task per arm for that reason.

A second effect: roughly one run in fifteen loses the model's prompt cache, which costs two to three times a normal task and says nothing about either tool. Worse, it lands unevenly — the first task of a sweep always starts cold. Those runs are excluded and counted.

Turn count and tool output are the steady signals; cost is the noisy one. Turns matter most, because a turn re-sends the entire context. Recall is reported at 99% against git's 100% — gita is very slightly behind on quality, and that is not rounded away here.

the loop that produced this

The cost number is a bug detector

Every cost regression turned out to be a correctness or robustness defect wearing a cost disguise — an encoding crash on a piped Windows shell, history that said when but not what, Rust impl Trait for Type quietly losing the trait, and 159 test names burying the one API change that was asked about.

The quality number is a better one

A single recall miss led to finding that TOML and YAML value changes were being classified as cosmetic and filtered out — gita was answering “no material changes” for a dependency version bump. That sat inside a task scoring −41% for nine iterations, because a cost win was masking a correctness hole.

speed

Separate from the agent evaluation, and measured directly. Answering “how did this function change over twenty commits” once took 12s, of which 6.5s was 98 git subprocesses at roughly 67ms of process spawn each. Parsing was never the bottleneck; asking was.
