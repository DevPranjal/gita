How to use it

gita is a drop-in replacement for reading a diff. If you know git diff, you already know it.

install

requires Python 3.11+pip
$ pip install gita $ gita diff HEAD^ HEAD

For the MCP server: pip install "gita[mcp]".

the commands

the whole surfacecli
$ gita diff uncommitted work, untracked files included $ gita diff HEAD^ HEAD one commit $ gita diff main HEAD a branch or a pull request range $ gita show <name> exact hunks for one entity $ gita history <name> how one function changed, with the code $ gita expand <id> open a rolled-up line $ gita serve run the MCP server
flagwhat it doeswhen
--interface-only only changes that can break a caller reviewing for breakage, or deciding whether a bump is safe
--patch a plain unified diff with noise removed you want hunks, just fewer of them
--filter TERM narrow to names or paths containing TERM large change, one area of interest
--budget N hard cap on output tokens a tight context window
--brief summary only, no code orienting before drilling in
--json machine-readable payload scripting, or feeding another tool

-C <path> selects the repository. git's spellings work where they mean the same thing: --stat, --oneline, --base/--head, --no-pager. Bare names work too — gita history fetch, not just gita history svc.py::fetch.

reading the output

gita diffgita
3 files | 12 changes | 2 interface | 638 noise filtered files: src/flask/app.py (modified), src/flask/ctx.py (modified) src/flask/app.py::Flask::do_teardown_request [signature_changed] src/flask/helpers.py::_CollectErrors (+4 nested) tests/test_ctx.py (9 tests: 7 added, 2 body_changed)
  • The headline counts what changed and how much noise was removed. You never need to see the noise.
  • path::Parent::child is an entity id. Pass it verbatim to show or expand.
  • (+4 nested) means changed children were rolled up. gita expand <id> opens them.
  • A test file on one line means bulk test churn was summarised. --filter that path to see each one.
  • On the working tree, files are marked (modified), (untracked) or (new) — so you do not need git status as well.

for an agent

The point of gita is that an agent picks it up without being told. Put it on PATH and describe it where your agent reads about the repository — an AGENTS.md, a system prompt, a skill file:

AGENTS.mdmd
Use `gita` instead of `git diff` to read changes. One command gives you the summary, the changed functions and the relevant code. gita diff uncommitted work, like plain `git diff` gita diff <base> <head> a commit or a range gita show <name> exact hunks for one entity gita history <name> how one function changed over time

Over MCP

gita serve exposes gita_diff, gita_show and gita_expand. Each layer is a separate tool rather than a depth parameter, so an agent sees the cost of a step in the name it chooses.
